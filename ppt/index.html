01 · 产品分析

Biomni 是什么：对话驱动的科研 Agent

目标用户是生物医学研究者 —— 一句话下达多步骤科研任务，Agent 端到端执行并交付可下载结果 + 可追溯过程。

核心用户路径（登录后实测，sess_57f6831fbe2d）

自然语言输入
+ 附件/文件夹→ 澄清
结构化问答→ 计划文档
Approve 审批→ 分步执行
待办打勾 + traces→ 结果文件
文件树/下载→ 迭代
fork / 追问

一次任务的状态机

input　clarifying　planning / running　success　failed(retry)　cancelled

刷新恢复是产品级特性：reload 后先拉快照渲染，仍 running 则重订阅续传，而非重跑。

产品洞察 → 改进切入点

Biomni 的痛点是过程半黑盒：线性待办无法表达步骤依赖、并行分支、哪一步卡住。→ 这正是画布的机会（第 05 节）。

DOM 实测 hasReactFlow: false：官方网页版没有画布，我们的创新是差异化的。

详见 analysis.md §1–3

03 · 功能取舍

19 项功能逐一裁决：保核心、做差异、砍边缘

取舍原则：P0 保核心 loop 与状态完整 → P1 做画布差异化 → 其余一律降级/删除。

裁决功能理由
保留 ×6 任务输入与会话流 · 分步执行+待办 · 流式 traces · 结果文件树 · 加载/失败/重试/取消/刷新恢复五态 · 计划审批 产品核心闭环 + 作业硬指标，状态完整性优先
新增 ×2 任务画布（DAG 编排 + 实时状态） · Skill Hub 本地技能中心 Biomni 实测没有画布 → 真差异化；技能从远程市场降级为可审计的本地注册表
简化 ×2 澄清（多轮 → 单轮）· traces（全量 → 摘要+折叠） 保留 waiting 状态语义，砍实现成本
删减/降级 云盘 · 计算面板 · 分享协作 · 多模型 · 搜索/网格 · fork/追问建议 · 赞踩反馈 依赖账号/多用户/云资源，与核心 loop 无关

降级方案（不可复现 ≠ 放弃）

登录鉴权 → 单用户本地运行｜云端沙箱 → 每任务独立沙箱目录 + 真实本地 Agent 执行｜对象存储 → 本地文件 + SQLite 元数据。每项在 README 标注真实接口替换点（如 executeStep() → 沙箱调用）。

详见 analysis.md §4 / §7

04 · 前后端闭环

真实 Agent + 事件溯源，不是 Mock 演示

后端调用真实 QoderCN Agent（非 mock），每个任务在独立沙箱内规划、调工具、落盘产物。

┌──────────┐  REST   ┌────────────────────────┐
│ Browser  │────────▶│ Next.js Route Handlers │
│ React 19 │         │  创建/快照/取消/重试     │
│ Zustand  │◀────────│  /stream  → SSE        │
└──────────┘   SSE   └───────────┬────────────┘
                                 │
              ┌──────────────────┼───────────────┐
              ▼                  ▼               ▼
        ┌─────────┐  emit  ┌──────────┐    ┌──────────┐
        │ runner  │───────▶│ provider │───▶│QoderCN   │
        │ 生命周期 │        │ 消息→事件 │    │SDK 真Agent│
        └────┬────┘        └──────────┘    └────┬─────┘
   appendEvent(先落库)                          │ 工具调用
              ▼                                 ▼
        ┌─────────┐ publish ┌────────┐   ┌─────────────┐
        │ SQLite  │────────▶│ pub/sub│   │ .data/       │
        │ EventLog│         └────────┘   │ sandboxes/…  │
        └─────────┘                      └─────────────┘

事件溯源 = 刷新恢复的根基

每个事件先写 SQLite EventLog（单调 seq）再广播；重连时先订阅、再重放 after=seq、按 seq 去重 → 断线/刷新后画面与实时流严格一致。纯 reducer 跨端共享，快照与实时流渲染同一份折叠逻辑。

全部真实验证过

Bash→Write→Bash 工具链真实执行，沙箱落盘 data.csv + report.md；112 条事件入库重放；running 中取消 → interrupt() 真生效；五态全部真实触发。

工程边界

Token 仅存服务端环境变量，不进前端/仓库；任务沙箱目录隔离；服务重启残留任务标记 failed，杜绝僵尸态。

05 · 前端创新（方案一）

任务画布：把线性待办升维成实时 DAG

节点 = 步骤，边 = 依赖；Agent 在干什么、卡在哪一步，一眼可见 —— 直接服务"严谨、可控、可追踪"。

交互能力

节点展示 · 拖拽布局 · 连线编排 · 缩放/平移 · MiniMap · 点击节点看该步 traces/产物

状态着色

pending　running(脉冲)　success　failed　waiting　cancelled(划除)

两种模式

观察态：实时状态推送，只读；编排态：审批前可增删节点、改连线，计划编译进 Agent prompt

题目要求我们的答案
组件CanvasView(React Flow 容器) / StepNode(memo 自定义节点) / NodeDrawer，与右栏面板共享同一 store
状态管理Zustand 单一 store，按节点 id 局部更新；SSE 事件 → store action；布局(视图态)与任务(数据态)分离
性能节点 memo + 视口裁剪；SSE tick 批量合并再写 store，避免整图 re-render；大图降级只读静态布局

06 · AI 辅助开发与质量

不是让 AI 替我写项目，而是把它放进工程流程

OpenSpec 规划 → 模块边界委派 → Prompt 约束 → 验证修正，每轮只推进一个垂直切片。

读上下文
作业/DOM/SDK 类型→ OpenSpec 拆解
proposal·design·spec·tasks→ 按模块委派
Provider/Runner/UI…→ 自动验证
test·typecheck·冒烟→ 人工 Review 修正
补约束·记录经验

规格驱动（OpenSpec）

需求先变成有边界、有验收标准的任务。例：「新任务空白会话」change 拆成 4 组任务、6/6 完成后归档，规格同步进主 specs。

Prompt 四要素

Context（读哪些文件/类型）· Task（只改哪个模块）· Constraints（不能动什么、必须复用什么）· Acceptance（跑哪些命令判定完成）。

质量门禁

npm test 10/10 · typecheck 0 错 · ESLint · 系统冒烟（创建→轮询→SSE 去重）· 人工回归（画布/取消/刷新恢复）。全部结果见 ai_usage.md。

关键原则：先读上下文再让 AI 动手；先跑验证再接受结果。AI 生成代码必须可检查、可回归。

07 · 边界与规划

诚实的边界，清晰的下一步

已知限制均来自真实取舍，不是遗漏；每条都有对应的解法设计。

已知限制

· 单机内存态 runner，未做分布式队列
· SSE 单向，运行中不能插话（以重试/新任务表达）
· 画布编排是 prompt 软约束，非硬性调度引擎
· 产物只列文件名/大小，未内联预览
· 无鉴权多租户

下一步（P1）

· runner 外置 worker + 任务队列 → 多实例部署
· 画布硬编排：步骤级调度引擎，运行时动态改图
· 产物内联预览（图片/表格）+ 运行中追加指令

一句话总结

我不是让 AI 替我写一个完整项目，而是把 AI 放进一套有规划、有边界、有验证的工程流程 —— 交付的是一个能真实跑通核心闭环、并带差异化创新的改进版原型。
