# 技术设计

## 背景

当前客户端把选中的项目保存在 `Sidebar` 的局部状态中，而任务状态管理、任务 API 和 SQLite 数据库都把任务视为一个全局集合。侧栏已经有基础的折叠/展开逻辑，但没有项目设置控件。数据库结构调整后，现有任务仍必须可用。

## 目标与非目标

**目标：**

- 让项目选择成为共享的工作区上下文。
- 让任务列表、任务创建、流式执行和任务操作都遵循当前项目。
- 增加缺失的项目设置入口，并对齐线上项目顶部和侧栏控件。
- 提供确定性的数据库迁移和测试覆盖。

**非目标：**

- 本次不实现完整的团队权限模型或远程项目协作。
- 不替换现有 SSE 协议。
- 不扩展云盘持久化，仅保留项目边界，为后续文件能力预留空间。

## 技术决策

### 1. 在 SQLite 中持久化项目及任务归属

新增项目表，保存稳定 ID、名称和时间戳；任务表增加非空 `project_id`。既有任务统一迁移到默认的“快速任务”项目。相比只在客户端筛选，这种方式能保证 API 请求、页面刷新和多标签页对任务归属的认知一致。

### 2. 在任务状态管理中显式维护项目上下文

状态管理统一维护 `projects` 和 `activeProjectId`，提供项目选择动作，并让任务刷新使用当前项目。切换项目时关闭当前 EventSource，必要时清空任务详情，再加载新项目的任务。这样侧栏只负责展示，不会重复实现上下文逻辑。

### 3. 在 API 边界强制执行项目范围

任务列表和创建接口读取或接收项目 ID；任务详情、消息、取消、重试、批准和流式接口都必须验证任务存在并保留其所属项目。服务端是最终权威，不能信任客户端为已有任务随意指定项目。

### 4. 首版项目设置支持重命名和受保护删除

增加可见的项目设置控件，并打开当前项目的设置界面。首版支持修改项目名称和删除项目，不实现归档、权限管理或其他项目管理能力。删除必须经过二次确认；只有不包含任务的项目才允许删除，默认“快速任务”项目不可删除，从而避免任务数据被意外级联删除。

### 5. 保留现有折叠逻辑并对齐展示

保留当前宽度过渡和展开入口，同时调整顶部结构、按钮顺序、文案、图标和区块折叠交互，使其匹配线上页面。使用 `选择项目`、`项目设置`、`折叠面板` 作为稳定的无障碍名称和测试选择器。

## 风险与取舍

- [迁移不一致] 既有数据库可能没有新字段 → 使用幂等迁移，并把所有旧任务分配到默认项目。
- [SSE 残留事件] 切换项目后旧流仍可能发事件 → 关闭旧流，并根据当前任务 ID 校验事件再应用。
- [隐藏耦合] 部分路由可能假设任务是全局的 → 审查所有任务路由和运行恢复逻辑；后台恢复保持全局，界面读取按项目隔离。
- [视觉漂移] 线上布局可能变化 → 在测试中固定结构和无障碍要求，颜色和间距继续使用 CSS 变量。

## 迁移计划

1. 创建并初始化默认“快速任务”项目，把已有任务迁移到该项目。
2. 同步部署服务端和客户端，使所有任务请求都能使用项目 ID。
3. 验证旧任务出现在“快速任务”中，切换到空项目时显示空状态。
4. 回滚时保留新增的项目表和字段，并暂时让所有读取默认使用“快速任务”；不删除任务数据。
